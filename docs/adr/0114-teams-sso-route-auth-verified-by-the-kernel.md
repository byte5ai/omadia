# 0114 — `auth: 'teams-sso'`: the kernel verifies Teams tab tokens for plugin routes

## Status

Accepted

- **Date:** 2026-11-25
- **Deciders:** Marcel Wege (owner, decision of 2026-11-01); implemented for #1620 in
  PR #1653.

## Context and Problem Statement

This record is retroactive: it documents a decision that is implemented on main.

After #1596 a plugin route registered as `'session'` needs an omadia operator session on
every prefix. A plugin page shown as a Microsoft Teams tab has no such session; it only has
a Teams SSO token for the signed-in Teams user. Hand-written plugins could validate that
token themselves (`auth: 'custom'`), but a plugin generated by the Builder cannot, and
`@omadia/channel-teams` already carried a private copy of the verification. Builder pages
answered 401 inside Teams. Who verifies a Teams tab token, and whom does it admit?

## Decision Drivers

- Generated plugins must work in a Teams tab without shipping token-validation code.
- One verifier, not one per plugin.
- The surface must stay behind the same operator consent as any other public path.
- An omadia operator session and a Teams user are different populations; they must not mix.

## Considered Options

- **A — A fourth kernel route auth mode, `'teams-sso'`, verified by the kernel.**
- **B — Each plugin validates the token itself** (`auth: 'custom'`).
- **C — Exchange the Teams token for an omadia session** (Teams users become operators).
- **D — Leave Teams tabs to operators only** (session cookie inside the iframe).

## Decision Outcome

Chosen option: **A**.

- **Registration and consent.** `ctx.routes.register(prefix, router, { auth: 'teams-sso' })`
  is accepted only beneath a prefix the plugin declared in `permissions.public_paths`, and
  the route is reached only through the granted public-path mount. No grant: 404.
- **The gate** (`auth/teamsSsoGate.ts`) reads `Authorization: Bearer` and nothing else. It
  is bound once per route entry, inside the disposed guard.
- **The verifier** (`auth/teamsSsoVerifier.ts`) accepts a token only with: `alg` RS256 and a
  valid signature against the tenant's Entra JWKS; `tid` the tenant of a configured bot and
  `iss` that tenant's v1/v2 issuer; `aud` that bot's app id (bare, or `api://<host>/<appId>`
  only for the deployment's own host); `azp`/`appid` one of Microsoft's Teams/M365 clients;
  `scp` and `oid` present (a delegated user, never an app-only token); no foreign `idp`;
  `exp`/`nbf` within 5 minutes of skew; at most 16 KB.
- **Audiences** (`platform/teamsSsoAudiences.ts`) are the bots of the installed, active
  `@omadia/channel-teams`, read per request. No active Teams channel: every token is
  refused and no key is fetched.
- **Key discovery.** Only a configured tenant reaches JWKS discovery. Keys are cached 1 h
  per tenant; an unknown `kid` refetches at most every 5 minutes; a failed fetch backs off
  60 s and keeps serving cached keys; fetch timeout 5 s.
- **Failure.** One fixed `401 auth.teams_sso_required` with `WWW-Authenticate: Bearer`,
  `Cache-Control: no-store`, `Vary: Authorization`. The reason goes to the server log only.
  A verifier crash is a refusal.
- **Pure.** A session cookie neither opens nor is consulted by a `'teams-sso'` route.
  Identity reaches the handler as `req.teamsSsoUser = { oid, tenantId, appId, upn? }`; the
  gate deletes any pre-set value first.
- **Builder codegen** keeps the browser page `'session'` and adds a Teams surface under
  `/p/<slug>/teams`: a data-free `'public'` shell plus a `'teams-sso'` data router whose
  first middleware refuses a request without `req.teamsSsoUser`.

### Consequences

- 🟢 **Good:** Generated and hand-written plugins get Teams tabs without validating tokens.
- 🟢 **Good:** A host that does not know the mode cannot serve the data router openly: the
  router fails closed and the generated manifest requires `compat.core >=1.51.0`.
- 🔴 **Bad (accepted risk, owner decision):** every member of a bot's tenant passes. A
  generated page renders the same tool data for each of them. The operator grant of the
  prefix is the consent to that reach; narrowing it without code means "Assignment
  required" on the bot's enterprise app in Entra, or authorising on `req.teamsSsoUser.oid`
  in a hand-written handler.
- 🔴 **Bad:** `@omadia/channel-teams` still uses its own copy of the verifier.
- ⚪ **Neutral:** A real Teams-tab login also needs the Entra "Expose an API" setup on the
  bot's app registration; the kernel cannot provide that.

## Pros and Cons of the Options

### A — Kernel mode `'teams-sso'`

- 🟢 One verifier, one JWKS cache, bound by the kernel like the session gate.
- 🔴 A fourth auth mode in the plugin contract.

### B — Plugins validate themselves

- 🟢 No kernel change.
- 🔴 #1596 showed that plugins promised this and did not do it; generated code cannot.

### C — Exchange for an omadia session

- 🟢 Reuses every session-gated route.
- 🔴 omadia has one role, administrator; every Teams user would become one.

### D — Operators only

- 🟢 No new surface.
- 🔴 A Teams tab is for the team, not for the operator.
